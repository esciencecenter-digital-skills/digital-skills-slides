Software inherently contains <i>value</i>, not a throw-away artifact <br> Can/should it be reusable by others? ...including yourself? Note: If you've spent any time at all writing software, at the very least it contains the value of the time you put into it. Furthermore, it represents the research or process you've encoded into it, and the experience you've gained by writing it. Wouldn't it make sense to not throw that value away? == <!-- .slide: data-state="standard 10" --> ## Reusability <div style="display: flex; gap: 1em;"> <div style="flex: 3;"> <ul> <li>Amount of reuse is hard to predict <ul> <li>By whom? <li>Which parts? <li>Which projects? <li>Reproducibility of results &mdash; from publications! </ul> </ul> </div> <div style="flex: 2;"> <img src='./media/image11.png'> </div> </div> Note: A lot of widely used software started out as someone's personal project. While most quick scripts won't grow into the next numpy or pandas, if your software proves useful to others, the amount and breadth of users may well grow over time. Do you think such growth is more or less likely if the code is hard to reuse? === <!-- .slide: data-state="standard 10" --> ## When should you have considered how to engineer your software? <div style="display: flex; gap: 1em; align-items: center;"> <div style="flex: 2;" class="blockquote-wrapper fragment"> <div class="blockquote"> The best time to plant a tree is 20 years ago. The second best time is now. </div> </div> <div style="flex: 1;"> <img src='./media/image12.png'> </div> </div> === <!-- .slide: data-state="standard 10" --> <!-- Some vertical space to have the lists not be at the top of the slide --> <br> <div style="display: flex; gap: 1em; font-size: smaller;"> <div style="flex: 1;"> <h3>Programming / Coding</h3> <ul> <li>Focus is on implementation <li>Writes software for themselves <li>Mostly an individual activity <li>Writes software to fulfill research goals (ideally from a design) </ul> </div> <div style="flex: 1;"> <h3>Engineering</h3> <ul> <li>Considers the <i>lifecycle</i> of software <li>Writes software for <i>stakeholders</i> <li>Takes <i>team ethic</i> into account <li>Applies a <i>process</i> to understanding, designing, building, releasing, and maintaining software </ul> </div> </div> <div class="blockquote-wrapper fragment"> <div class="blockquote" style="margin: 30px auto 0; font-size: smaller;"> Programmers tend to start coding right away. Sometimes this works. <h4>&mdash; Eric Larsen, 2018</h4> </div> </div> Note: What's the difference between programming and software engineering? === <!-- .slide: data-state="standard 10" --> ## Target Audience <div style="font-size: smaller;"> A researcher developer, with foundational coding skills, now facing new challenges - Software projects becoming more complex - Scale of development increasing - More collaborative development and use, internal or external - Higher expectations on software - Increase in requests for change, more 'technical debt' </div> <img width="800" src='./media/Slide17.jpg'> === <!-- .slide: data-state="standard 10" --> ## Course Outline <div style="font-size: smaller;"> 1. Environment for Collaborative Code Development - Project setup, IDEs, virtual environments, Git(Hub), style conventions 2. Ensuring Correctness of Software at Scale - Automatic testing, unit tests, continuous integration, debugging 3. Software Development as a Process - Software development process: requirements, design, architecture and implementation (via programming paradigms) 4. Collaborative Software Development for Reuse - Code review, documenting and preparing/packaging software for reuse 5. Managing and Improving Software Over Its Lifetime - Tracking issues, managing communication and project planning </div> === <!-- .slide: data-state="standard 10" --> ## How will the workshop run <div style="font-size: smaller;"> Delivery is helper-supported self-learning (no live coding) - We will introduce each part with a short presentation - Learners go through material individually (at their own pace) - You work together in groups of 4-5 people - Trainers will be available to assist with problems and answer questions - Initially exercises are performed individually, more group/team work in later stages when we will need to keep more in sync with everyone in a group - Feel free to ask questions and start discussions with people in your group or instructors. This is a good opportunity to ask related questions about your daily work as well. - We will remind you to take regular breaks </div> === <!-- .slide: data-state="standard 10" --> ## A final note ... <div style="font-size: 0.7em;"> About working through the material - Start from the actual section introduction - bigger picture - Exercises - try to do them on your own (before looking at the solution) - Exercises - don't skip them! Some later materials depend on this - Optional exercises are clearly marked - all other exercises should be completed - Please finish the section in the rest of the week if you were not finished. Note that section 1 is a bit bigger than the other sections. - We wrap up together at the end of the day. If you finish the section early you can work on the optional exercises in the collaborative document Please ask for help - do not suffer in silence! - Ask for help if needed - We know from experience that it can be hard to stay focussed at the end of the day, especially if you feel like everyone else is moving faster than you. Ask an instructor to help instead of getting stuck! </div> === <!-- .slide: data-state="standard 10" --> ## The story ... <div style="display: flex; gap: 1em;"> <div style="flex: 2;"> You have just joined a team that works on an existing software project.
